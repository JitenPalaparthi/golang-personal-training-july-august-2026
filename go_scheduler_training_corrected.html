1. Normal goroutine creation
The compiler lowers a go statement to runtime goroutine creation. The runtime calls runqput(..., next=true), which prefers the current P's runnext. If occupied, the displaced G goes toward the regular local run queue.
2. When does work reach the global queue?
Important examples: (a) a P's local run queue is full—Go's slow path moves a batch (roughly half the local queue plus the new G) to the global queue; (b) runtime injection has no current P; (c) some injected runnable work is placed globally to wake idle Ps. The scheduler also periodically checks global work for fairness.
3. Work stealing
If a P has no runnable work, a spinning M searches other Ps. It can steal runnable work from another P's local queue (roughly half in the common queue-steal path), balancing work without routing everything through the global queue.
4. Netpoller
For pollable network I/O, the G waits instead of tying up one OS thread per connection. OS-specific polling (for example epoll/kqueue/IOCP) reports readiness. The runtime turns waiting Gs runnable and injects them back into scheduling.
5. Blocking syscall
A blocking syscall is different from pollable network waiting. If an M is stuck in a syscall, its P can be handed off so another M can continue executing Go code. The runtime may wake or create an M when necessary.
6. P count vs M count
Ps represent the resources required to execute Go code in parallel and are governed by GOMAXPROCS. Ms are OS threads. The runtime may have more Ms than Ps because some Ms can be blocked in syscalls or otherwise occupied.
